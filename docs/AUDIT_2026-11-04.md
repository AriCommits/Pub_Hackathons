# Project and Track 3 compliance audit

Audited checkpoint: `7d090b5` on `master`, created before this audit. Its source tree matches `68faaa3`; source changes were already committed. The checkpoint is intentionally empty. Untracked `.agents/` execution records and ignored datasets/model artifacts were not added. Nothing was pushed.

Scope: the available plans (`plan_1.md`, `plan_1/OVERVIEW.md`, plans 3–8), method/submission notes, training, routing, verification, saved evaluation results, and current official hackathon rules. Plan 2 is absent from this checkout; historical execution records are not a substitute for its requirements. Historical GPU execution ordering and artifact immutability cannot be independently certified from today's files.

## Conclusion

The implemented training is supervised LoRA fine-tuning on gold trajectories, followed by inference-time prototype routing and argument regeneration. It is not RL. This is useful as an SFT baseline, consistent with the user's clarified intent. Preserve it and compare an actual rollout-trained policy against it under matched conditions.

Most of plans 3–8 landed. The major gaps are in the experimental design and older unfinished requirements: no working RL trainer, no substantive AgentTune/AuditKIT pipeline, contaminated curriculum evaluations, a verifier that does not enforce required tool execution, and no current-adapter router-off baseline.

The [official track page and rules](https://hackathon.lexsi.ai/) explicitly put RL in the reliable-tool-calling problem statement. Other Track 3 problems include efficiency and distillation, so SFT is not categorically outside Track 3. Track 3 is exempt from the two-repository minimum; the page still asks for actual use of the track stack. Local compatibility classes alone do not demonstrate that use. Public HF artifacts and multiple before/after metrics are required. This is a technical assessment, not an eligibility ruling.

## Priority findings

### 1. High: GRPO is a non-training stub

`scripts/train_grpo.py:main` passes `dataset=[]`, prints metadata, ignores the distinction between normal invocation and `--plan-only`, and returns success. `actproto/training/grpo.py:try_create_trainer` only imports the factory and reports its type; it never calls it. Reward names are strings in a payload, and the imported `reward_from_metrics` is unused. There are no sampled training rollouts, policy-gradient updates, or saved RL adapter here.

`actproto/training/lora_run.py:run_lora_sft` uses TRL `SFTTrainer` with assistant-only loss. `sft_dataset.py:gold_to_sft_row` replays scripted gold calls. Executing tools to construct supervised examples does not turn the objective into RL. `scripts/train_aligned.py` is also payload-only, despite returning success without `--plan-only`.

This is largely deliberate scope rather than failed implementation: `docs/SUBMISSION.md` says “GRPO) is post-MVP,” and the original brainstorm calls a GRPO run optional. It nevertheless leaves the reliable-tool-calling RL objective unfulfilled.

### 2. High: curriculum evaluation contains exact training prompts

CPU probes found **38/38** evaluation prompts from `order_tasks(1)` in the `order_tasks(4)` training set, and **266/266** format evaluation prompts in `order_tasks(2, formats=ALL_FORMATS)`. The first repetition has identical arguments and outputs, not merely similar wording. Plan 8 also explicitly fits prototypes on those format prompts (`scripts/extract_activations.py`).

Plan 7 acknowledges: “an in-distribution check, not a held-out set.” Thus this follows that plan but cannot substantiate held-out generalization. Plan 8 inherits the same limitation. Keep these as training-distribution diagnostics; reserve genuinely unseen compositions, arguments/entities, and prompt families for the RL comparison. The original 104-task test has also repeatedly informed subsequent changes and should be treated as a development benchmark for future claims.

### 3. High: success reward allows bypassing required tool execution

`actproto/evaluation/metrics.py:score_episode` assigns `task_success` from the final outcome only. `cases.py:task_to_case` constructs final-state/answer assertions; it does not enforce the reference trajectory. `harness.py` lets `finish` set `done` and `answer` directly.

Reproduction: for the first `order_tasks(1)` task, a scripted policy calling only `finish` with the expected answer scores `task_success=True`; gold is `calculator, search_docs, finish`. The audit supplies the known answer only to demonstrate the verifier loophole, not as evidence that a trained policy knows it. Memorization makes that shortcut plausible on exact training repeats.

`docs/METHOD.md` promises “Fabricated assistant text does not pass.” The implementation verifies answer equality, not provenance or required tool use. Answer-only verification can be appropriate for some tasks; it is insufficient for tasks explicitly requiring ordered execution or as the sole RL reward for reliable tool use. Use trusted execution records and task-specific constraints, while allowing valid alternative solutions where the task permits them.

### 4. High: external toolkit integration is not demonstrated

`docs/SUBMISSION.md` claims an AgentTune-compatible/AuditKIT-compatible repo chain and says local stand-ins apply when packages are absent. The audit environment has neither package installed. Real SFT directly invokes TRL; `try_agenttune_sft(..., trainer_factory=None)` only reports a payload. `Project` and evaluation cases/runner are local implementations. `try_auditkit_episode` has no caller in the source tree. The optional harness import is not evidence of a completed AgentTune training run.

This misses the brainstorm's “These two are the pipeline.” Add and validate actual toolkit integration before describing the submission as that pipeline; compatibility is currently unverified against installed toolkit versions.

### 5. High: best result does not isolate SFT or the router's contribution

The saved `B2apchain` result is **104/104**, but uses the assistant-only adapter, prototype routing at hop 1, argument regeneration/fallbacks, and a four-step cap. `B1` is the earlier full-sequence-loss adapter and predates later decoding fixes. There is no router-off run for the assistant-only adapter in `trial.yaml`.

`docs/METHOD.md` asks whether prototypes improve success relative to ordinary LoRA. Historical B1 versus B2apchain changes training and inference together and cannot establish that causal claim. Keep historical results; add matched current-harness comparisons for SFT and RL, with the same adapter initialization, tasks, budgets, decoding, and fallback settings. Report router-on and router-off separately.

### 7. Medium: format prompts omit the required answer convention

Plan 8 says the finish answer remains the tool values joined by `|`. `_sequence_prompt` explicitly tells the agent to do that. `_header_prompt` supplies only execution instructions and the catalog: no joined-value answer convention or finish instruction. The global system prompt only says finish with the answer. The header-format oracle therefore demands a format the prompt does not specify, confounding a comparison intended to vary layout. This is a benchmark specification gap even though the plan's example headers also omit that instruction.

### 8. Medium: export and reproduction instructions lag the chosen baseline

`trial.yaml:export` selects only `results/adapters/b1`, processed data, and logs. It omits the better assistant-only/order/format adapters and their prototype/threshold files. Generated curriculum training data is not included in the original processed dataset export. Local artifacts exist, but public hosting and collection links were not verified.

README's initial reproduction sequence extracts only train activations by default, whereas building thresholds requires validation rows. Its training command now produces assistant-only SFT at the historical `b1` path, so it cannot reproduce the old full-sequence B1 result and can overwrite that preserved baseline. Later-adapter recipes also omit their extraction/prototype-building steps. `EXPERIMENT_STATUS.md` opens with a stale November 2 running-job warning contradicted by later completion entries. These are reproducibility and handoff gaps, not evidence that a job is currently running.

### 9. Medium: efficiency metrics are too weak for an RL objective

`repeated_calls` compares adjacent tool names only, so distinct useful calls to the same tool count as repeats while nonadjacent loops may escape. `unnecessary_calls` counts names absent from the gold tool set, so surplus calls to permitted tools escape. `tool_call_f1` is bag-of-names F1, not order correctness (prefix accuracy is reported separately). Before using these for optimization, distinguish identical state/argument repeats, failed executions, and excess calls relative to valid task completion.

## Recommended SFT-to-RL comparison

Keep `b1_assistant_only` as the initial SFT baseline candidate and preserve all saved results. First close verifier loopholes and freeze an unseen evaluation set. Measure that adapter on the current harness with routing disabled and enabled. Then initialize RL from the same adapter, generate actual tool-interaction rollouts on training tasks, compute task-specific rewards from trusted execution, and update policy weights through a real trainer. Keep the router disabled for the primary training comparison; evaluate its incremental effect separately. Report verified outcome, required-tool compliance, argument correctness, invalid executions, steps, and latency on identical held-out tasks. Do not assume RL will outperform SFT; that is the experiment.

This audit does not implement that new experiment or rewrite the earlier plans.
