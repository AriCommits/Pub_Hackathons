# Reward specification

`verified_success_v2` is the primary reward: exactly `1.0` when the shared `verification_v2.verify` reports strict verified success, otherwise `0.0`. A nonempty answer, correctly shaped text, task ID, model-declared success or a copied observation never grants credit. The ledger records the verifier's answer and compliance results, reasons and the component counts for the same task.

`TrustedRewardSession` is an in-process boundary for a trusted orchestration layer. It owns a fresh harness, executes each submitted call through `execute_event`, and constructs an `ExecutionTrace` from those captured events. It does not deserialize rollout JSON or accept model-supplied events. The trusted caller must provide the correct isolated fixture harness and must never let the policy mutate the harness or task. Python objects, provenance strings and the session class are not an authentication or sandbox mechanism; a caller that supplies a forged harness or events defeats this contract. The current Plan 10 rollout collector serializes traces, so the later training integration must retain a live trusted session or perform verified replay against the isolated fixture. Do not score arbitrary serialized traces as trusted.

The optional, separately named `bounded_shaped_v1` is `S - 0.10*min(I,3) - 0.05*min(D,3) - 0.05*S*min(E,4)`. `S` is strict verified success; `I` is the count of invalid parsing/schema/forbidden attempts and unexpected tool errors; `D` counts repeated calls with the same tool, arguments and state before the call; `E` is the number of calls beyond an explicitly declared nonnegative `oracle.valid_call_bound`. If the bound is absent, excess is omitted and the ledger explains why. The excess penalty is success-conditioned. The maximum penalty is 0.65, so all successes outrank all failures. Declared, ordered expected errors are not invalid merely because later dependencies are missing; duplicate occurrences are not automatically excused. `bounded_shaped_v1` gives no partial-progress or format reward.

`bounded_prefix_v1` uses that same penalty and adds failure-only prefix credit. `k` is the number of `required_tools` dependencies matched by the ordered walker in `TrustedRewardSession.score`: a dependency counts only when every parent in `after` is already matched and the call matches the tool, the exact arguments, and any declared state or expected error. `n` is the number of those dependencies. `finish` and `no_tool` do not add credit. A later dependency whose parents are unmet does not count. Unmatched calls, repeats, and token length do not increase `k`. Credit is computed from the live session events. A forged event raises instead of scoring. `FAILURE_CEILING` is `0.30`, strictly below the lowest shaped success `0.35` (`1 - 0.65`). When `S` is true the reward is `1 - penalty` and prefix credit is not added. When `S` is false and `n == 0` or `k == 0`, the reward is `-penalty`, at most `0`. When `S` is false and `k >= 1`, `progress = 0.30 * (k / n)` and `previous = 0.30 * ((k - 1) / n)`, and the reward is `min(progress, max(previous + 0.01 * (0.30 / n), progress - penalty))`. A prefix of `k` stays strictly above a prefix of `k - 1`. A full correct prefix that still fails the terminal answer tops out at `0.30`. There is no length bonus. `score_executed_session` still returns `bounded_shaped_v1`.

A session accepts calls until explicitly scored once; timeout, truncation and parse failures must be represented by the trusted orchestrator. Session finalization does not itself prove that an individual policy or tool call was subject to a hard timeout. Group advantages are population-standardized per supplied reward group. A constant group returns exact zeros and increments the zero-variance diagnostic; callers must ensure all rewards in a group belong to the same public task and current behavior policy. Non-finite rewards are rejected. Reward constants and caps are fixed by the version; `actproto/configs/reward_v2.yaml` documents those values and is not interpreted as a dynamic override.

The shared verifier determines success for each trace. It validates declared dependency arguments, finish consistency, state continuity and supported recovery behavior. Any change to verifier, fixture, normalization or task semantics requires a new version and matched reruns of both controls; do not tune rules against held-out data. This reward is designed for deterministic synthetic tools and makes no general safety claim.

## Live collector handoff (fixture only)

`collect_scored_fixture_episode` in `actproto.training.rl_rollouts` creates a fresh manifest-verified scoped `ToolSession` and a `TrustedRewardSession` in the same process. Every tool call passes once through that `ToolSession`, and both the reward recorder and the v2 collector capture it. It compares the independent live captures and shared-verifier results before returning the locally computed ledger. Caller-supplied sessions and unscoped fixture factories are rejected. Failure events are counted by the reward session; a mismatching record or capture raises instead of returning a score. The ledger and record are returned to the trusted caller, not inserted into policy prompts. A stored JSON row is still not authenticated execution evidence.

The live Tiny Aya train path does not use a finish-substring reward. `_executed_trace_reward` returns 0 for a decoded completion that contains the word finish when no in-process tool session was captured. When a session was captured, it calls `TrustedRewardSession.score` with `bounded_shaped_v1` and does not add a length term. A stored JSON row is still not authenticated execution evidence. `TrustedRolloutAdapter` accepts in-process behavior sampling only for the trainer callback and only with a deadline. It still rejects deserialized JSON, caller-supplied sessions, and unscoped fixtures. `collect_episode` remains fixture-only. Python callbacks remain trusted and must not be given object references that let them mutate the tool session.
