# AgentTune compatibility investigation

AgentTune source revision `d4db4c12d52342227c4113a70183d0f64aa2f345` (1.1.3), TRL 1.7.1, Python 3.12.13 and the exact resolved packages are recorded in `requirements-rl.lock`. Install in an isolated environment, not the existing SFT environment. The lock was resolved on Windows; it does not prove Linux compatibility.

`agenttune.core.backend_factory.create_agentic_trainer("grpo", backend="trl", ...)` returns a wrapper; `setup_data()` and `setup_trainer()` construct the actual `trl.GRPOTrainer`. A local random GPT-2 fixture and two prompts constructed it successfully with batch size 2, two generations, beta 0, and CPU. No optimization was run. The wrapper introspects TRL arguments and silently ignores unknown keywords, so our adapter rejects unknown options. AgentTune combines reward functions and routes tools through its rollout function. Source exposes `env_mask`, but its use for actual sampled tool observations remains unverified.

The cached Tiny Aya tokenizer rendered a calculator call, observation as a user turn, and finish with prefix-preserving token IDs. `episode_token_mask` demonstrates template-span masks only: it does not establish that AgentTune's sampled token IDs, termination handling, or TRL loss match those spans. A real fake-policy tool loop and comparison against backend `env_mask` remain mandatory before this gate passes.

The resolved PyTorch 2.11.0 wheel reports `2.11.0+cpu` and CUDA unavailable on this machine. This environment cannot run the planned GPU study; do not use it for GPU training without resolving and verifying a compatible CUDA build. No Plan 9 S7 frozen baseline is available, so optimization is independently blocked by the plan's cross-plan gate.

Run `python scripts/check_rl_backend.py` in the isolated environment with the Tiny Aya tokenizer cached. It constructs a real trainer and probes the tokenizer, but intentionally exits nonzero while the rollout mask is unverified. A factory import or wrapper alone is not proof of trainer readiness.

A live fake-engine probe through the installed `create_rollout_fn`, using the real Tiny Aya tokenizer and calculator/finish callables, made three generation decisions. The second saw the actual calculator observation, but the third ran after `finish`, so the upstream loop does not implement this project's finish termination. Its completion IDs insert `tokenizer.encode(str(result), add_special_tokens=False)` rather than the complete user-turn serialization, while generation sees `Tool result:\n...` wrapped by the chat template. Consequently the model context and likelihood token sequence do not match. `env_mask` marks the raw result tokens zero, which alone does not fix the missing wrapper. Its default fallback system prompt also changes the tool instructions. These are concrete blockers: use a verified adapter/rollout implementation or a proven compatible backend before enabling training; do not assume the default loop is safe.

The adapter now also contains a CPU fixture loop that stops at `finish` and assembles exact sampled action IDs with full template spans. It rejects non-prefix-preserving renderings, masks injected observations and template-only tokens, and has unit tests for incorrect sampled IDs and missing termination. It is a feasibility fixture, not wired to the installed optimizer or a production collector; the trainer gate remains closed. `scripts/check_rl_backend.py` exercises it using the cached Tiny Aya tokenizer and contrasts it with the installed AgentTune loop.

An additional installed-trainer probe supplied a custom rollout mask `[1, 0, 1]` through the actual AgentTune wrapper. TRL returned the same `tool_mask` in `_generate_and_score_completions`; this establishes mask propagation for the tiny fixture, not zero gradient at every observation token or correctness of the project's real rollout. The probe does not run an optimizer step.
